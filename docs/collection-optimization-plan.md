# 采样首试接纳与协议诊断优化计划

实施状态：三个阶段已完成本地验证；结果、源码指纹及未验证范围见[实施报告](reports/first-attempt-buffer-2026-09-13.md)。服务器复测及公网并发对比仍为后续手动步骤。
编写日期：2026-09-13。下文保留实施时采用的目标、约束与验收标准；各项实际验证结果以实施报告为准。

## 1. 事实与目标

服务器测试运行约 30 分钟，二进制 SHA-256 为 `8a926ae2921d1afb912538b842c074128fdb6939a217a97ec2f038fe7747cd25`，与本地 Release 可执行文件一致。原始材料位于 `state/logs/bt-sniffer.2026-09-13.log` 和 `state/logs/public-test-20260913-212240/`；这些本地材料不随 Git 分发。

已确认的结果：

- 约 3.5 秒首次发现 hash，IPv4/IPv6 有效 DHT 响应分别为 2,603/2,259；上一轮本机约 42 分钟的冷启动没有重现。
- 保存 101 个 hash、创建 84 个任务、提交 34 份 metadata；初始采样中的 17 个 hash 接近 30 分钟仍未创建任务。
- 启动约 5 秒后暂停采样，累计暂停约 29 分 55 秒，没有恢复。结束时 50 个任务处于 retry_wait。
- announce 可按总容量接纳，其任务又计入近期活跃量；近期活跃量持续超过 16，阻止采样及近期补建。
- 1,141 次 TCP 尝试中，785 次建连超时、152 次其他 I/O 失败；标准握手仅超时 3 次。扩展协商出现 67 次 Protocol、62 次 Reset，具体协议原因尚不明确。
- worker 执行耗时合计约占四个槽位可用时间的 98%，包含网络等待，不是 CPU 利用率。不能沿用上次本机“worker 空闲”的判断解释服务器全部表现。
- 数据库完整性、外键、34 份 metadata 的 SHA-1 及正常退出检查通过。

本轮目标：在总容量允许、worker 持续结束任务的前提下，让已保存的近期无提示 hash 获得首试机会；让退避存量和有提示任务不直接锁死该首试额度；定位扩展协商错误的具体类型。

不承诺持续高输入下每个 hash 都在 30 分钟内处理，也不承诺新策略必然提高成功吞吐。增加首试服务可能减少提示任务或重试的实际服务量，需同时报告产出和等待。

## 2. 保持的边界与明确的行为变化

保持单线程 Tokio、SQLite 专用线程、事务、generation 保护和正常退出。默认并发仍为 4，保留现有 TCP/握手/任务期限、每 hash 串行连接、DHT 配额、六次远端失败休眠及再次观察后的再激活规则。不修改 UI，不新增 CLI 开关或外部依赖，不删除历史数据。

四类领取及其 4∶2∶1∶1 轮转保持不变，提示不绕过退避，完成提交后立即补位。公平份额属于**领取类别**，不等于采样/announce 来源份额；已有 hash 得到有效提示后可以转为 Hint。

以下规则明确替代上一轮 freshness 设计：

1. 近期首试缓冲额度不再统计 generation > 0 的任务，也不统计具有有效提示的任务。
2. freshness 的无提示采样新任务统一由补建入口创建，避免新到批次抢先占用刚释放的额度。保存 hash 到创建任务通常增加至多一个维护 tick 的等待；扫描分页、存储压力或额度不足时可能更长。
3. 旧 `recent_active` 继续报告真实近期活跃总量，但不再作为采样高低水位输入。新日志显式记录所用的背压依据。

这些变化仅适用于同时启用 sample/fetch 的 freshness 模式。capacity、仅采样、仅采集沿用原接纳与背压规则。

## 3. 阶段一：先补诊断并冻结比较基线

### 3.1 扩展协商与 I/O 原因

在现有 `PeerError`/`WireError` 边界引入固定错误原因枚举，由产生错误的位置设置；中文 Display 从类型生成，不匹配错误字符串分类。

第一批应区分以下原因：

- Bencode 结构错误、根类型错误、尾随字节。
- 字段类型错误、整数范围错误、扩展映射类型错误、扩展 ID 范围错误。
- 扩展消息缺少 ID、协商完成前收到 metadata、metadata 大小非法或传输中改变。
- 其他既有 peer-wire 错误按实际发生位置补齐固定类别，不将无法识别的问题默认为某个具体原因。
- 对 `Io` 增加固定子类，如 ConnectionRefused、NetworkUnreachable、HostUnreachable、PermissionDenied、Other；保留原来的 EOF/Reset/Timeout 分类，记录的是操作系统返回的错误，不推断根因。

新增 `peer_failure_detail` 聚合事件，包含 stage/source/family/reason/count，区分 total/interval。每次失败只记录一次细分原因；成功和取消不伪造错误。保留现有 `peer_diagnostic`、旧四阶段聚合及任务最终失败类别，旧字段不静默改义。记录错误原因不改变重试计数、超时范围和网络流程。

维度全部来自有限枚举，不引入 hash/IP/客户端字符串/原始 errno 标签，不打印原始报文或 metadata。不得为了让 Protocol 数量下降而放宽 Bencode、长度、分片或 hash 校验。

### 3.2 采样等待与接纳诊断

复用已有 `SamplerStatus`，每分钟按地址族补充 candidates、in_flight、successful、failed、unsupported 和真实 pause 原因，区分没有候选、冷却、输出背压、collector 暂停、存储故障。已有字段不足以区分的状态在状态拥有者处补齐，不从零发包量猜测原因。

新增接纳摘要：总活跃量、近期活跃总量、近期等待首试量、B/高低水位、使用的背压依据、本区间近期补建数/历史补建数/扫描数，以及可加和的拒绝或延后原因。

“延后次数”按入口观察或扫描定义，不能冒充去重 hash 数。待补建 hash 数和年龄可在分钟级按需查询，须验证查询计划与开销；不要为输出 gauge 每秒全表扫描。现有扫描中实际见到的最老候选，应标明是扫描范围内的观测值。

启动记录 `admission_policy_version` 和 `backpressure_basis`，保留 run_id、有效配置和包版本。基准报告另存源码清单、工具链和可执行文件 SHA-256。

本阶段不调整调度、接纳或协议兼容策略。增加固定输入夹具后，先运行现有策略，封存基线结果及对应源码，保护当前暂存区，不用 Git 历史改写保存基线。

## 4. 阶段二：把近期额度改为首试缓冲

### 4.1 计数口径

设总活跃容量为 M、worker 并发为 C：

```text
B = min(M, 4 × C)       # 首试缓冲上限，默认 16
R = min(B, M − 1)       # 历史补建预留，M=1 时为 0
Q = 近期等待首试任务数
```

Q 同时满足：

- `first_seen` 在 `[now − 30 分钟, now]`，重复观察不延长首次发现时间。
- `generation = 0`，状态为 pending 或 retry_wait。正常运行中尚未领取的任务是 pending；不能只凭状态名把 generation=0 的兼容记录算成已重试。
- 没有未过期且符合当前 AddressPolicy 的提示，判定与领取 Hint 类使用同一契约。

Q 不要求 due_at 已到期：它限制等待首试的存量，未到期任务同样占缓冲。领取时仍必须到期。

有提示任务、正在运行的任务以及 generation > 0 的任务不占 Q；它们继续占总活跃容量 M。领取事务递增 generation 后立即释放一个首试缓冲名额，不必等该 hash 成功或休眠。

不新增任务来源字段，不把“没有提示”等同于“必定来自采样”。提示失效后的未首试任务也可进入 Q。

### 4.2 统一补建与事务边界

freshness 模式下，采样批次继续在事务内保存全部 hash；无提示新任务不再由当前批次直接插入，而是交给统一补建。已有任务不重复创建，重复观察和合法 dormant 再激活保持原契约；再激活不重置 generation，不重新冒充首试。

近期补建沿用 first_seen/hash 分页，每 tick 最多检查 128 条；历史补建最多检查 128 条，合计不超过 256。额度不足时保留当前位置，不能跨过尚未接纳的候选；扫描到底回绕，延迟插入到游标之前的记录由后续扫描处理。顺序保证按扫描批次及游标定义，不宣称对任意乱序到达实现严格全局 FIFO。

近期新任务接纳必须同时满足 `active < M` 和 `Q < B`。统计、插入及本批额度扣减在同一 SQLite 事务内，扣减以实际插入结果为准。已有 metadata 或重复 hash 不消耗额度。

补建和批次保存分别是有界事务；保存成功但尚未补建是一种正常持久状态，不表示丢弃。超过 30 分钟仍未补建的 hash 进入历史补建范围；已经创建的任务继续由领取规则按当前年龄分类，不删除、不驱逐。

地址策略由启用采集时的具体接纳配置传入存储；样本保存、补建和统计共用同一策略。不能把生产的 PublicOnly 硬编码到 loopback 测试，也不能为每个入口复制一套提示有效性判定。

### 4.3 announce 与历史的边界

announce 保留按总容量 M 接纳、满载时刷新已接纳任务提示的能力，保留提示数量/有效期与退避约束。有效提示任务不占 Q，因此不会仅因 announce 存量增加而直接耗尽无提示首试缓冲。

历史补建仍只在总活跃量低于 `M − R` 时创建任务。R 只限制历史补建，不是对 announce 的硬隔离；announce 仍可能用尽 M。发生这种情况时容量暂停优先，不能承诺新采样任务继续接纳。

提示过期、失效或旧库恢复可能让已有任务转入 Q，使 Q 暂时超过 B。此时不驱逐旧任务，只停止新增补建和主动采样，等待领取释放额度。B 是新增接纳的事务上限，不是所有动态分类变化下永远不超过的数据库不变量。

### 4.4 背压与补位

每 5 秒使用 Q 判断 freshness：达到 B 暂停采样，降至 `floor(B/4)` 或以下并持续 30 秒恢复，默认仍为 16/4。每次有效检查高于低水位时清空恢复计时。

总容量、磁盘、存储暂停继续做 OR，首试低水位不能解除其他暂停。旧 `recent_active` 再高也不直接触发 freshness 暂停。minute 摘要保留该旧 gauge，并新增 Q 和 basis，明确旧 backlog 布尔值表示采样策略暂停、其依据已由版本字段标识。

协调器每秒先处理硬保护，再执行有界补建和领取；每 5 秒对更新后的首试缓冲做背压检查，避免刚补满 Q 就依据旧快照错误恢复。worker 结果提交后仍立即领取补位，补建保持 tick 预算，不因每次完成额外扫描 256 条。

若已有大量未补建近期 hash，首试缓冲可能持续满载，主动采样仍可暂停；此时应看到已有 hash 持续获得首试。该策略优先消化已保存候选，不保证在已有首试积压时持续增加采样输入。

代价：首试失败后不再占 Q，可能更快积累 retry_wait；M、退避和休眠仍提供总约束。必须同时报告活跃增长、各类等待及成功提交，不能只用恢复次数评价收益。

## 5. 阶段三：必要回归与固定输入验收

### 5.1 存储、调度与背压

- 50 个近期 generation > 0 的退避任务、总容量充足、Q=0 时，不得因这些任务单独维持 freshness 暂停；恢复经过完整 30 秒低水位观察。
- 持续合法 announce 不直接占 Q；初始无提示 hash 可补建并获得 Recent 领取。提示过期、无效地址、重复刷新及未到期提示任务都按同一契约处理。
- 大批样本全部保存，近期新任务只通过统一补建创建；连续新批次不能通过即时插入绕过已等待的扫描候选。
- 覆盖延迟批次、跨页、游标回绕、30 分钟边界、暂时超 B 的旧任务、M=1—4、事务回滚、重复批次、dormant 再激活和旧 generation 结果。
- 四类持续非空时八次领取保持原轮转；空类借用正确。领取释放 Q 后可再次补建，网络失败不把任务放回首试计数。
- capacity、仅采样、仅采集行为保持；硬容量耗尽、磁盘及存储故障不能被低 Q 绕过。

### 5.2 两个固定输入比较

在隔离临时数据库中比较阶段一基线与新策略，均为并发 4。调用真实存储事务和领取逻辑，不只对公式做数组模拟。

1. **退避存量场景**：50 个近期退避任务，下一次到期在 5 分钟后，另输入 34 个无提示近期 hash；首试固定耗时 1 秒并成功。允许采样器读取受控输入，明确在途批次。验收新策略下 34 个 hash 在 15 秒逻辑时间内全部首次领取；首试缓冲消化后，主动采样在 45 秒内恢复或始终未被暂停，不能等待旧任务到期。
2. **持续竞争场景**：9,000 个历史任务、50 个退避任务、64 个有提示任务，初始输入 34 个无提示近期 hash；600 秒逻辑时间内，每 10 秒新增一个采样 hash、每 5 秒一个合法 announce。任务固定耗时 5 秒；使用固定成功/失败序列和确定性退避。本组总活跃量预先核算保持低于 M，避免用硬容量失败解释首试机会。验收初始 34 个无提示 hash 的首次领取 P95 ≤180 秒，并且近期、历史、重试均持续获得服务。四类非空时近期每 8 次领取分得 2 次，四个 worker 每 5 秒完成 4 项，约每 5 秒可领取一项近期任务；阈值应包含扫描及 tick 余量，不能要求违反服务份额的等待时间。

第二组是对服务器负载形态的构造实验，现有日志和最终 SQLite 不包含完整逐事件历史，不能称为服务器运行的精确重放。新增到达表示已观察输入时应明确其不受采样暂停过滤；端到端的恢复行为由第一组或独立 collector/dispatcher 集成测试验证。

使用受控时钟跨越 30 分钟边界，不需要真实等待半小时。记录：全部 hash 数、待补建数量、首次领取覆盖数及年龄 P95、各类领取数/最长服务间隔、成功提交、活跃峰值、Q 峰值、暂停/恢复、扫描量及存储调用 P95。未领取样本单独计数，不能从 P95 中静默排除后宣布等待达标。

数值阈值只适用于上述固定服务时间与有容量夹具，不作为公网 SLA。若明确的服务模型无法满足阈值，先审查模型和调度，不通过放宽断言掩盖饥饿。

### 5.3 协议、日志与退出

每种新增协议原因有最小合法/非法报文回归，并用 loopback 验证原因能穿过完整 fetch 路径。覆盖未知扩展字段、嵌套字段、可选字段分次到达、ID=0、提前 metadata 消息、错误类型/范围、尾随字节、EOF/reset 和成功路径。

继续验证标准/扩展共用原 5 秒绝对期限，peer/任务外层超时与取消不被误记为协议错误。新增原因只增加观测，不改变网络发送顺序。需要修复兼容性时，先以具体子原因及最小报文复现，在独立改动中处理，不依据 67 次 Protocol 总数直接降低校验。

检查旧字段、事件节奏、run_id、阶段计数一次、区间清零和关闭尾段。任务成功数必须来自存储 Applied，网络成功和过期提交不能冒充落库。

退出等待 worker、DHT transaction、socket、连接许可和存储提交收尾；检查最终 running=0、未完成领取可恢复及 SQLite 关闭结果，不以取消通知或固定 sleep 作为完成证明。

执行项目检查：

```sh
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
```

新增固定输入比较以精确测试名显式运行，不批量运行 ignored。当前测试数和旧比较结果不是本轮验收通过证据。

## 7. 后续服务器验证

本轮实施不自动启动公网长测。后续先在隔离状态目录使用并发 4，至少覆盖**首次有效采样后 35 分钟**，同时观察持续 announce、近期补建及提示失效。另用旧库副本验证恢复与已有积压，原始服务器证据保持只读。

重点检查无提示 hash 是否持续获得首试、Q 而非全部 retry_wait 是否驱动背压、退避增长是否接近 M、提示/历史/重试是否均有服务，以及 Protocol 具体原因。首试缓冲一直满时应有相应领取进展，不能仅以“采样仍暂停”判定失败。

并发 4/8 的服务器对照放在规则稳定之后，分别记录网络输入、CPU/RSS、存储和成功产出；不把公网两次不同输入当严格固定负载比较，也不自动把默认并发改成 8。

使用 SIGTERM/Ctrl-C 正常结束并核对最终事件和数据库。若通过 timeout 运行，应同时记录包装命令和应用关闭状态，避免把包装命令的 124 直接解释为程序故障或独立验收通过。
