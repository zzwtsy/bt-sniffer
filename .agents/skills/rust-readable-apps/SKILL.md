# 可读的 Rust 应用

## 定位

为掌握基础 Rust、但不熟悉复杂借用和异步的维护者编写代码。目标是完成当前功能，让读者知道入口在哪里、数据归谁、步骤是什么、失败后如何收尾、规则应该改在哪里。

先控制功能范围，再明确职责，最后选择语法。不要把“专业”理解为更多配置项、抽象层、设计模式或高级类型技巧。正确性、安全和明确资源边界不能为可读性让路；在满足这些前提的方案中选最直接的一种。

输入是用户当前任务、适用的项目指引及相关源码。输出是范围明确的实现或有位置证据的审查结论，不是默认的架构升级计划。

## 1. 读取上下文并确定范围

读取适用的 `AGENTS.md`、相关入口和调用者、已有测试、`Cargo.toml`、锁文件及工具链约束。使用实际依赖版本和 feature，不从记忆假定 API、MSRV 或运行时配置。只有依赖 API、语言机制或安全行为确需核实时，再查匹配版本的官方资料。

先区分任务类型：从零实现、增加功能、保持行为的重构、改变需求的简化、只读审查。只读审查不改文件。已有程序中，“去掉环境变量支持”“并行改串行”“修改日志格式”属于行为变化，不伪装成整理代码。

新功能或跨模块改动先用几句话说明：当前必须完成什么、不新增什么能力、实现归属、状态所有者及验证方法。小修复不强制提交计划书。不要仅因存在轻微可选项就反复追问；采用可逆且安全的简单默认，并在必要处说明假设。

## 2. 先消除不必要的能力

对每个新参数、环境变量、依赖、配置对象、trait、枚举策略和扩展点，判断它是否对应当前调用者或真实部署要求。

| 当前情况 | 默认选择 |
| --- | --- |
| 所有调用者都采用相同策略，部署也无需覆盖 | 直接固定；有业务意义的值就近命名 |
| 两个现有调用者确实需要不同文件名前缀 | 只保留前缀参数，不顺便设计完整日志配置 |
| 只要求终端和文件输出 | 直接建立两个输出层，不自动支持环境变量、JSON 切换和热更新 |
| 仅因两段配置相似而想封装泛型工厂 | 保留容易对照的重复 |
| 必须实现框架接口，或隔离真实测试/替换边界 | 使用最小必要抽象，限制影响范围 |
| 想为未来需求保留未调用函数 | 不新增；已有入口先查真实使用者和兼容要求 |

固定策略不等于到处散落魔法值，也不等于增加一个包罗万象的 `GlobalConfig`。常量放在拥有规则的模块附近。不要把密码、令牌和真实部署差异写死，不省略外部输入校验，不擅自删除现有资源上限。

日志、配置等基础能力优先组合成熟库，不自行构建注册表、后端适配框架或监控子系统。参见[固定日志策略](references/examples.md#logging)。

## 3. 让目录反映职责与所有权

新增模块之前明确：它负责什么、不负责什么、谁调用它、它拥有哪些状态。无法用一句具体的话说明职责，就先不要拆出该模块。

独立业务模块统一采用 `模块名/mod.rs`，叶子模块也如此；编译目标入口和小型内联测试按 `AGENTS.md` 的例外处理。`mod.rs` 可以容纳直接实现；不要求所有模块都继续拆出 `service`、`impl`、`types` 和 `error`。

目录按实际功能与变化原因组织。应用负责资源组装和生命周期；业务模块负责自己的流程；存储负责数据库操作。该划分是思考工具，不是必须预建的三层模板。小 CLI 不自动拥有 `app/service/repository/domain` 全套目录；不只为将来复用拆 workspace 或公共 library。

整理时检查：

- 名称与职责是否对应。运行会话不能藏在名称暗示“仅持久化”的模块里；`utils`、`common` 不能成为无归属代码的收纳箱。
- 依赖是否迫使底层理解上层应用。对于双向引用，先考虑由各模块报告自己的结果、由上层解释；不要直接引入事件总线或抽象接口体系。
- 状态是否有明确所有者。多个文件给同一巨型结构体实现方法，不自动代表职责已经隔离；也不必为形式给每组字段创建对象。
- 可见性是否最小。先考虑私有、`pub(super)` 和必要的 `pub(crate)`；不用全部 `pub` 解决移动后的访问错误。

迁移目录时同步模块声明、导入、测试选择路径和文档链接。不要用 `#[path]`、`include!`、重复导出或新的通配导入掩盖混乱。旧项目先整理当前受影响范围，不把一次小修复变成全仓迁移。参见[目录与依赖](references/examples.md#modules)。

## 4. 把主流程写成清楚的业务步骤

函数集中完成一个主要任务，内部步骤处于相近抽象层次。出现以下情况时重新划分职责：调度循环直接包含完整的下载、重试、数据库操作和统计；多个分支重复更新同一规则；需要同时记住很多可变状态；宏体里很难找到主要动作。

把独立规则和完整步骤提取为具名函数，必要时移入职责模块。不要只把长函数拆成 `step1`、`do_work`、`process_inner`，也不要用“初始化状态 → 状态管理器 → 管理器工厂”增加跳转。

行数是线索，不是验收指标。线性的配置组装可以集中写；复杂 SQL 即使只有一行仍应展开。生产实现与测试分别评估，不能删注释、压缩表达式或机械拆函数来达标。

优先提前返回、`?`、`let … else`、具名条件和直接循环；配置 builder 链可以保留。复杂计算或副作用不要压进迭代器链、`map_or_else` 和多层闭包。宏内同样主动分行，SQL 展示字段、条件和事务关系。

提取函数前后逐项比较校验顺序、事务范围、超时范围、并发推进方式和取消效果。不为易读把并发查找改成先查完再下载，不随意跨 `.await` 移动状态更新。参见[流程拆分](references/examples.md#flow)。

## 5. 用名称减少猜测，用类型消除真实歧义

名称描述实际行为及结果：`acquire_for_ip` 是申请许可，`connect_peer` 才是建立连接；`enqueue_job` 不是 `complete_job`。返回许可的对象应叫 `ConnectionPermit`，不误称 `Connection`。

变量采用业务名，时间、长度等易混淆数据写清单位。局部循环索引和含义明显的短变量可保留；不盲目拉长所有名字。

默认使用具体类型。返回值有多个容易混淆的业务字段时，用小型具名结构体；普通二元结果或同类集合无需全改成新类型。布尔值表示真实的开关或事实，不把一串布尔参数作为隐藏的模式选择器。

保留能阻止无效数据流入下一阶段的类型，例如已校验结果、当前领取标识。不要为了避免“复杂类型”把它们全部换成原始字节、字符串和 bool。也不默认使用类型状态模式。参见[语义命名](references/examples.md#names)。

## 6. 中文注释覆盖理解边界

先简化不必要的设计，再解释保留的设计。注释与代码同步编写，不等实现结束后批量补模板。

| 位置 | 应说明的内容 |
| --- | --- |
| `//!` 模块说明 | 业务职责、主要入口、协作对象；复杂模块补充状态/任务由谁持有及阅读顺序 |
| `///` 类型与非简单函数 | 业务用途、重要参数与单位、返回值、失败/副作用；只写本处适用的信息 |
| 关键字段、枚举分支 | 状态含义、不变量、不同结果的区别，不只翻译标识符 |
| `//` 实现注释 | 规则原因、边界处理、为何借用/克隆/加锁、取消与资源释放 |
| 使用示例 | 正确保存 guard、处理返回结果、说明必要前提；片段标明省略的上下文 |

简单 getter 和显而易见的赋值不重复解释。不要求每个函数都套参数、返回值、错误三段空模板；也不因函数不是 `pub` 就省略关键契约。

特别核对：`Ok(None)` 与出错、`Applied` 与 `Stale`、入队与提交、通知取消与确认退出、后台日志与持久落盘。注释不能承诺代码没有实现的保证。修改签名、返回分支和生命周期时，搜索相应文档与示例并同步更新。参见[返回契约](references/examples.md#contracts)。

## 7. 降低借用和异步的局部复杂度

只临时读取就借用，需要保存或交给独立任务就明确所有权。遇到借用问题，先缩小作用域、分离步骤或调整数据归属，不先四处补 `clone`、`Arc`、`Mutex` 和生命周期参数。

廉价复制可以换取清楚的代码，但解释必须真实：`Arc::clone` 是共享所有权，不等于复制业务数据；大缓冲区克隆不能描述成廉价句柄复制。只有确有热点证据时，才用复杂借用和零拷贝提高实现难度。

根据 I/O 和框架需求决定是否异步；简单同步 CLI 不默认引入 Tokio。已有项目保持其 runtime 与 feature 约束。单一状态所有者常比共享可变状态更容易理解，但不强行把所有任务改为单线程。

每个新增后台任务、通道和锁都应能回答：谁持有，容量是多少，何时结束，谁处理结果，取消后哪些工作仍可能继续。关键边界用中文解释。`tokio::spawn` 的 `Send + 'static` 不代表数据永远不释放；不为了满足约束泄漏内存。

同步锁不跨 `.await` 持有；异步锁也尽量缩短持有范围。不能把阻塞数据库或文件操作直接放进敏感事件循环。已有 `spawn_blocking` 或专用线程的工作，不能仅凭外层等待超时就声称底层已经停止。

保留需要的并发上限、载荷预算、重试和清理顺序。取消通知、任务回收、数据库确认是不同步骤。重构这些部分时，核对项目已有的异步专项指导；没有专项 skill 也应依据相关 API 与测试检查，不要求额外安装一组技能。参见[所有权与异步](references/examples.md#ownership)。

## 8. 错误处理与验证不追求形式统一

应用边界使用项目已有的错误方式，并补充必要的动作、路径和原因。内部需要区分恢复策略时保留有意义的错误类型；不要过早全部转成字符串，也不只为风格引入新的错误框架。

外部输入与可恢复 I/O 错误不使用 `unwrap`/`expect`。测试断言和明确的不变量可以使用，并写明真实前提。不要悄悄吞错、重复记录同一错误，或把“请求被接受”当“业务已成功”。

按 `AGENTS.md` 与现有 CI 选择格式、编译、Clippy 和测试命令。不自动升级依赖、启用全部 features、整组 restriction 或新质量门禁。纯注释、文档或 skill 修改不虚构业务测试结果。

测试保护可观察行为。使用临时目录、局部 subscriber、受控时钟或同步信号等合适机制；不为简单业务做大型 mock 框架，不替依赖重测全部内部实现。宏体排版与目录结构仍需人工阅读，编译器不会代替这部分审查。

## 9. 完成前用维护者视角复读

检查 diff 和受影响调用链，回答下面的问题；简单任务不必把全部问题打印给用户。

1. 本次功能入口、主要步骤、状态归属和修改位置是否容易找到？模块名能否帮助定位？
2. 是否新增了没有真实用途的配置、预留接口、依赖、抽象或转发层？能删除而不是再包装吗？
3. 是否有职责混合、双向依赖、误导命名、过深嵌套、紧凑宏体或 SQL？拆分是否实际减少理解负担？
4. 中文注释是否解释本处关键机制？示例、返回语义、资源释放与实现是否一致？
5. 行为、校验顺序、任务取消、事务和资源边界是否保持或按要求改变？相关测试是否真的执行？

实现任务简要交付“改了什么、如何验证、未验证项/风险”。只读审查按位置给出问题与影响，区分确定错误、可读性建议和待验证猜测，不把主观目录偏好说成编译错误。不默认追加重构路线图、评估报告或大量说明文件。
