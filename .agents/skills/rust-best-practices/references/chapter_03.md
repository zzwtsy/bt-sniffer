# 第 3 章：性能证据

## 先明确观测对象

性能修改应说明工作负载、指标、基线和可接受的成本：吞吐、尾延迟、内存峰值、CPU、磁盘或网络可能是不同瓶颈。先定位瓶颈再改代码，不把一次微基准的收益推广到完整服务。

- 使用与目标部署相符的优化配置；通常是 `cargo build --release`，而 `cargo bench` 默认使用 bench profile。自定义 profile 以项目配置为准。
- 控制输入规模、并发、缓存冷热与测量噪声，保留可重复的比较。没有统一的“超过 5% 就值得改”标准。
- CPU flamegraph 的宽度反映采样占比，纵向深度反映调用栈；栈深本身不说明 CPU 成本高低。排队或 I/O 等待需要额外的延迟与队列指标。
- 比较前后行为一致性；移除校验、放宽持久化或静默丢弃失败不属于等价优化。

## 所有权、分配与布局

先确认成本发生在哪里，再决定是否克隆、借用或装箱：

- 移动 `Vec`/`String` 通常转移其指针、长度和容量，不复制整个缓冲区。引用计数克隆与深拷贝需要分开评估。
- 数组存储位置取决于其所有者，可能在栈、堆、静态数据或 future 内；“数组必定在栈上”不成立。
- 大数组按值移动、较大的 future 或深层调用可能增加栈/任务内存。`Box::new(large_value)` 不保证消除构造时的栈临时值；需要时从 `Vec` 或其他堆分配 API 直接构造。
- `SmallVec` 依据选择的内联容量保留内部空间，超出容量才转到堆；它不是大型固定数组的自动优化方案。
- 没有通用的 24/512 字节阈值。按真实类型布局、调用频率及平台测量，避免为了尺寸增加多余的间接访问。

## 迭代与抽象

`for` 与迭代器组合都可能被优化为高效循环。`collect()` 是否多余取决于是否需要拥有结果、重复遍历或隔离后续 I/O；`.sum()` 与 `.fold()` 的选择也不能单凭语法推导运行时速度。

泛型可以支持内联与专门化，但会增加编译量和代码体积；动态分发可能减少二进制大小。对热路径测量后再决定，详见[第 6 章](chapter_06.md)。

只有证据支持时添加 `#[inline]`、布局调整或缓存。缓存还要说明失效、容量和一致性，否则只是把计算成本转移成状态成本。

参考：[Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)、[Rust Performance Book](https://nnethercote.github.io/perf-book/)。
